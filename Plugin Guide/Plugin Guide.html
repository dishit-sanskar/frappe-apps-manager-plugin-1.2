frappe-apps-manager · Claude Code plugin

Build an ERPNext app from requirement documents

How to take a BRD, To-Be process or FRS and turn it into a working ERPNext v16 custom app with /frappe-build-from-docs: one feature slice at a time, with you approving every flow, the plan and each slice.

Frappe / ERPNext v16.53+ local bench dev site + test site git-tracked app

What it does

Claude runs as the orchestrator. It runs every bench command and hands focused work to specialist agents. Nothing moves forward without your approval at three kinds of gate: the business flows, the build plan, and each finished slice.

Phase 0PreflightChecks bench, sites, app, MCP
Phase 1RequirementsBusiness Analyst: register, fit-gap, flows
Gate 1Flows approvedYou tick each flow
Phase 2DesignArchitect: design.yaml, slices
Gate 2Plan approvedYou tick the build order
Phase 3–4Slices, then sign-offBuild, test, review each slice; docs at the end

A slice is one business document end to end: its DocTypes, fields added to standard DocTypes, server logic, form UI, print formats, reports, permissions and tests. The next slice starts only when every item of the current one is approved.

Who does what

PhaseAgentProduces
1 RequirementsBusiness Analyst01-requirements.md, 02-fit-gap.md, flows.yaml
2 DesignArchitectdesign.yaml for all slices; ADRs for real decisions
3 LogicDeveloperControllers, overrides, services, server tests

One-time setup

  1. Create an API user on the dev site. Give it a separate login (e.g. ai-dev@local) with only the roles the agents need to read. Never use Administrator, and never use a production site. Open the user, go to API Access and click Generate Keys.

  2. Turn on MCP. System Settings → AI Agents tab → tick Enable MCP. It is on by default for new sites. No AI Agents tab means your Frappe is older than 16.53; update it first (see Troubleshooting).

  3. Save your connection settings in a file outside any git repo, for example ~/.frappe-mcp.env. The API keys only work on the site that issued them.

    export FRAPPE_SITE_URL=http://newproj.localhost:8000
export FRAPPE_API_KEY=your_api_key
export FRAPPE_API_SECRET=your_api_secret
export FRAPPE_PASSWORD=administrator_password   # for the browser check
# optional: company knowledge base shared across projects
export FRAPPE_KB_DIR=~/.claude/frappe-kb

  4. Test the MCP endpoint. Opening the URL in a browser shows "Only POST is supported", which is normal. Test with a POST instead:

    source ~/.frappe-mcp.env
curl -s -X POST $FRAPPE_SITE_URL/api/v2/mcp \
  -H "Authorization: token $FRAPPE_API_KEY:$FRAPPE_API_SECRET" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | head -c 400

    You should see tool names such as search_doctypes and get_doctype_schema. AuthenticationError means the key or secret is wrong, or belongs to another site.

  5. Load the plugin. While trying out a new version, point Claude at the plugin folder directly:

    cd ~/path/to/frappe-bench
source ~/.frappe-mcp.env
claude --plugin-dir /home/sanskar/Downloads/frappe-apps-manager/2.1.0

    To make it permanent, copy the folder into your marketplace folder, raise version in .claude-plugin/plugin.json (the install cache is keyed by version), then run /plugin marketplace update <marketplace> and reinstall. If an older copy is also installed, turn it off with claude plugin disable frappe-apps-manager@<marketplace>.

  6. Check inside Claude. /mcp shows plugin:frappe-apps-manager:frappe with a ✔. /agents lists the frappe-* agents. /hooks shows destructive_guard, task_guard, mcp_guard and agent_metrics.

Phase 0Preflight

Runs on every start and every resume. It checks versions, both sites, the server, the browser-check password, a clean app repo and the MCP connection. Then it asks you two questions, once per project, and records the answers in STATUS.md:

  • Commit approved slices automatically? If yes, each approved slice becomes one commit: feat: <slice title> (S03).
  • When to pause during a slice:
Pause modeStops for youUse when
on-issueOnly on failing tests, out-of-scope changes, schema requests or open questionsNormal work (recommended)
every-taskAfter every taskThe first slices of a new project, or after a plugin update
per-groupAfter all tasks of one DocTypeYou want a look per document
sliceOnly at the slice review checklistA well-known pattern you trust

You can change the mode later by editing the Pause during a slice: line in docs/spec/STATUS.md. The new mode applies from the next slice.

Phase 1Requirements and flow approval

  1. The Business Analyst converts the documents and writes a requirements register with stable IDs (BR-, FR-, PS-…), a fit-gap against standard ERPNext v16, and every business flow step by step. With MCP connected, it checks real fields and existing customisations on your site.

  2. One questionnaire. Every open question (OQ-) comes with a proposed default. You answer the ones that change scope or design, and can accept the rest as defaults in one go.

  3. Gate 1. You get docs/spec/review/flows-review.md, one item per flow and per assumption, each with an explanation, a Mermaid diagram, the steps, the roles involved, and what is standard versus developed. Review it (see Reviewing a checklist) and say review done.

Gate. Rejected flows go back to the analyst and come back in the next round with a note saying what changed. Phase 2 starts only when every flow is approved.

Phase 2Design and plan approval

The Architect writes docs/spec/design.yaml, the single source for every slice. It covers new DocTypes, custom fields on standard DocTypes, roles, workflows, reports and print formats, plus rules: (business rules with their document event) and requirements: (which code owns which ID). Slices follow the To-Be process with foundations first: roles, settings, warehouses. slice_tool.py validate must pass.

Gate 2: docs/spec/review/plan-review.md shows the build order and, per slice, what ERPNext already covers and what will be developed. Approve it the same way.

Existing project? The architect describes what is already built as slices marked generate: false. Those still go through a review checklist, so you approve them like any other slice.

Phase 3Slices, strictly one at a time

  1. Start. Claude records the base commit and tells you what the slice will deliver.

  2. Generate. Writes DocType JSON, custom fields, roles and workflows as fixtures, plus stub files from design.yaml. Each business rule becomes a method containing a TODO(rule FR-…) placeholder, and each rule gets a skipped test. Claude wires hooks.py and migrates both sites.

  3. Brief. slices/S03-<title>.md: the data model, rules and acceptance criteria the agents work from.

  4. Build in small tasks. The slice is split into tasks of at most 4 requirements each. The Developer and UI/UX lines run in parallel, with a checkpoint after every task. See Tasks and checkpoints.

  5. Integrate. Claude applies the agents' requests (usually hooks.py), migrates, clears the cache, and builds assets if public/ changed.

  6. Tester. Writes acceptance tests from the brief in tests/acceptance/test_s03.py and runs them with the slice's other tests on the test site. It reports failures, but never fixes product code.

  7. Fix. Each failure goes to the agent that owns the file, for at most 2 rounds. Still failing after that, Claude stops and asks you.

  8. Browser check. A headless browser logs in and opens every new desk page. Console errors, failed requests, error dialogs or blank pages go back to the owner. Screenshots are saved in slices/S03-shots/.

  9. Trace. # REQ: FR-xxx tags in the code are collected into the traceability matrix.

  10. Review checklist. slices/S03-<title>-review.md lists everything built, item by item, with links into the site. Claude stops and waits for you.

  11. Approval. Once every item is approved, the slice is marked approved and committed if you allowed that. Rejected items become lessons, and the slice is archived as a reusable pattern. After the first slice, Claude writes conventions.md for later slices to copy.

Tasks and checkpoints

Long agent runs are slow, costly and hard to follow, so each slice is cut into small tasks. A typical split for one slice:

LineTasks
DeveloperOne per new DocType controller · logic on each standard DocType (overrides, services) · report data · permissions · remaining rules
UI/UXForm and list view per DocType · form script per standard DocType · print format · report filters

How each task runs

  1. next takes a git snapshot, writes the task prompt (rules, conventions, lessons, earlier handoffs, function signatures, similar past slices) and arms the guard for that task's files.

  2. The agent works on that one task only. Low-complexity tasks run on a faster, cheaper model. The same agent is kept for the next task only if it is in the same DocType group, finished less than 5 minutes ago and has done fewer than 2 tasks. Otherwise a fresh agent starts, because a stale agent costs more to resume.

  3. The agent writes a short report, S03-tasks/T01.json, and replies with one line.

  4. checkpoint checks the work itself instead of trusting the report. Did the task stay within its files? Did a test run pass, as recorded by the guard? Does every requirement have a REQ: tag? Are any TODO(rule placeholders left?

What you see at a checkpoint

S01 T01 · Gate Pass controller (Developer)
Status: Done ✓ | Slice S01: 1 of 7 tasks done

What was done: Gate Pass checks vehicle number and blocks submit without security sign-off
Tests: 4 passed, 0 failed
Requirements covered: FR-001, FR-002
Files changed (2): …/gate_pass.py, …/test_gate_pass.py

Carried forward:
  • For the next tasks: factory make_gate_pass(vehicle) in tests/factories.py
  • To apply once no task is running: hooks.py - doc_events Gate Pass on_submit -> …
  • For your slice review checklist: Submit a Gate Pass without sign-off: it should be refused

Next: T05 Gate Pass form and list view (UI/UX, running now) · T02 Logic on Purchase Receipt (Developer) · …
Paused: pause mode is every-task. Say continue to go on.

When something needs you, a Needs your attention list appears instead, each point with a suggested action. For example: "No code is marked as implementing FR-003 (REQ: tag missing): either not done or not tagged. → Fix, or Continue if another task covers it."

Your choices at a pause

ChoiceWhat happens
ContinueThe task is accepted as is. Any open points stay listed for the slice review
Fix with my commentYour comment goes to the agent, and the task is checked again
Undo the taskOnly this task's files return to the snapshot, and the task starts again. The other line's work is untouched
Stop hereThe build stops. Resume later with the same command
Schema changes (a new field, a changed DocType) are never made inside a task. The agent asks for them, the architect updates design.yaml, and generate runs again.

Reviewing a checklist

The flows checklist, the plan and every slice checklist all work the same way. Open the file in your editor (Markdown preview shows the diagrams), check each item on the site, then save.

- [x] A1 New fields on Work Order appear in the right place … (http://newproj.localhost:8000/app/work-order/new) - Comment: - [ ] B2 Defined print formats shall be produced: Raw Material Requisition, Batch Manufacturing Record … - Comment: BMR print cuts the operations table on page 2
  • Approve: change [ ] to [x] and leave Comment empty.
  • Reject: write what is wrong after Comment:. The tick doesn't matter then.
  • Save, then tell Claude review done.

Rejected items go to the right agent and come back in the next round with a Fixed: note. Approved items stay approved. Requirement IDs appear only in hidden comments, never in labels users see.

Phase 4Finish

  1. Full test run of the app on the test site.

  2. Traceability check: every in-scope requirement must be Verified.

  3. The Technical Writer writes user-guide/<role>.md per role, following the To-Be processes, plus admin-guide.md.

  4. coverage-report.md: checker output, deferred items with reasons, assumptions still unconfirmed, review rounds per slice, time per step and agent metrics.

Pause and resume

You can stop at any time, close Claude, or hit a usage limit. All state lives in files, so nothing is lost. To continue, start Claude from the bench folder again and run the same command. It reads docs/spec/STATUS.md and continues from the first unfinished phase or slice. Approved slices are never rebuilt.

cd ~/path/to/frappe-bench && source ~/.frappe-mcp.env && claude --plugin-dir /home/sanskar/Downloads/frappe-apps-manager/2.1.0
# then, inside Claude:
/frappe-apps-manager:frappe-build-from-docs ../requirements/newproj --site newproj.localhost --test-site newproj-test.localhost --app newproj
  • Inside a slice, it picks up at the first task that isn't done, from slices/S03-tasks.yaml.
  • To redo a phase or slice on purpose, add --from 2 or --from S05.
  • After updating Frappe or ERPNext, ask Claude to migrate both sites and run the full test suite once before continuing.

Lessons and metrics

The company knowledge base ($FRAPPE_KB_DIR, default ~/.claude/frappe-kb) carries what you teach across projects:

  • review-log.jsonl: every item you rejected, with your comment.
  • lessons.md: short rules drawn from those rejections, added to every task prompt.
  • patterns/: approved slices (brief, design, patch). Later task prompts point to similar ones.

To see where time and effort went:

./env/bin/python /home/sanskar/Downloads/frappe-apps-manager/2.1.0/skills/frappe-slice-builder/scripts/slice_tool.py metrics --app newproj --slice S08

It lists minutes, tool calls, file writes, test runs and apps/erpnext reads for each agent run. A run with many ERPNext reads usually means MCP wasn't used.

Skills and agents alone

The full flow is optional. Every agent and skill also works on its own in any Claude session, for example:

  • "Use the frappe-developer agent to add a validation on Sales Order that…"
  • /frappe-apps-manager:frappe-migrate, /frappe-apps-manager:frappe-test, /frappe-apps-manager:frappe-new-doctype
  • "Use the frappe MCP to show the fields of Work Order."

Outside the flow, no task is active, so the task-scope guard and the token savers stay silent. The destructive-command guard and the MCP guard always apply.

Skills

Skills are packaged know-how: rules, reference and scripts for one topic. There are 93. You can call them three ways:

  • By name. "Use the frappe-print-format-builder skill to…" when you want a specific one.
